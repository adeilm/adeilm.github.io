Should you fine-tune your LLM? A plain guide to SFT, LoRA, DPO and GRPO

You have an AI model, like the one behind ChatGPT. It is smart, but it doesn't do exactly what you need. Maybe it doesn't know your company's documents. Maybe it answers in the wrong format. Should you train it, or just ask better?

"Fine-tune it" is the usual answer, and it comes with a pile of acronyms: SFT, LoRA, QLoRA, RLHF, DPO, GRPO. Each one solves a different problem and needs different data. This post explains them in plain words first, then gives the details for engineers.

I learned this while comparing these methods during a research internship this summer. There I wrote a decision guide to help engineering teams choose an approach, and built the first version of a RAG assistant that recommends one, with citations. Everything below comes from public papers and docs, listed at the end.

The post in 30 seconds

Question
My AI model doesn't do what I need. Should I train it?
Answer
Often not. First try a better prompt, and let it look things up in your documents (RAG).
Train when
You need to change how it behaves: a format, a tone, a narrow task, or a smaller model.
Start with
LoRA, a cheap way to train. Add DPO or GRPO later if you need more.

The billions of numbers inside a model. Training changes them.
Fine-tuning
Training an existing model a bit more, on your own examples.

First: do you need to train at all?

Most problems fall into one of two groups:

Missing knowledge

It doesn't know your documents or recent facts.

Give it the handbook: let it look things up.

Fix: RAG

Wrong behavior

It knows enough, but the format, tone or task is wrong.

Train the habit with examples.

Fix: fine-tuning

Research backs this up. Ovadia et al. (2023) found that RAG consistently beat fine-tuning on raw documents at adding knowledge. Gekhman et al. (2024) found that models learn new facts slowly through fine-tuning, and then make up more answers.

Either way, start with a good prompt and an eval set. Without them, you can't tell whether training helped.

My short version: RAG changes what the model can look up. Fine-tuning changes how it behaves.

Eight methods, as if the model were a new colleague

Imagine the model is a smart new colleague. Each method is a different way to teach them:

SFT

"Here are worked examples."

Supervised fine-tuning: pairs of a question and the ideal answer. The model copies the pattern.

LoRA

"Add a small notebook, don't rewrite the brain."

Freeze the big model and train a tiny add-on. Much cheaper.

QLoRA

"The same, on a smaller desk."

LoRA on a compressed model, so it fits on one GPU.

RLHF

"Hire a coach who scores every answer."

People rank answers, a scoring model learns from them, then the model trains to get high scores.

DPO

"This answer is better than that one."

Learns directly from pairs of better and worse answers. No coach needed.

GRPO

"Here is a test with an answer key."

A program checks each answer, like tests for code. Better-than-average tries are rewarded.

Distillation

"An expert trains a junior."

A big model's answers teach a small, fast model.

Merging

"Combine two specialists."

Mix the weights of two fine-tuned versions of one model. No training at all.

The trick that made training cheap: LoRA

A model's weights are huge tables of numbers. Full fine-tuning changes all of them, which needs a lot of GPU memory.

LoRA freezes the big table (W) and trains two thin tables (B and A) beside it. Their product is added to W. Drag the figure to turn it:

Against full fine-tuning of GPT-3 175B, LoRA cut the trained parameters by 10,000× and GPU memory by 3×. QLoRA goes further: it compresses the frozen model to 4 bits, so fine-tuning a 65B model needs under 48 GB instead of over 780 GB.

The catch is in the title of one study: "LoRA Learns Less and Forgets Less". It learns less than full fine-tuning, but it also damages less of what the model already knew.

Which one should you pick?

Ask these questions in order. The first "yes" tells you where to start.

On one GPU with 24–48 GB of memory, use QLoRA. The steps also stack: a common path is SFT first, then DPO or GRPO.

My rule of thumb

Change the cheapest thing first: prompt and evaluate, retrieve for knowledge, and train only to change behavior.

Build one fixed eval set on day one, and change one thing at a time. If you add RAG, LoRA and DPO in the same week, you won't know which one helped.

SFT with full fine-tuning

Show the model input → ideal output pairs and update every weight. Quality beats volume: LIMA got strong results from 1,000 curated examples. Compute is very high (about 112 GB for a 7B model with mixed-precision Adam, before activations, per ZeRO). On code and math, it learned more than LoRA at common ranks, but forgot more outside the target domain (Biderman et al., 2024).

Save full fine-tuning for lots of data, several GPUs, and a LoRA run that has plateaued.

LoRA and QLoRA: a minimal setup (code)

LoRA adapters merge back into the model with no extra inference latency, which makes it the right first training run. QLoRA keeps the base model in 4-bit; long sequences still add activation memory.

Minimal setup (PEFT docs); drop the 4-bit parts for plain LoRA:

Show code python · 24 lines
import torch
from transformers import AutoModelForCausalLM, BitsAndBytesConfig
from peft import LoraConfig, get_peft_model, prepare_model_for_kbit_training

bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_use_double_quant=True,
    bnb_4bit_compute_dtype=torch.bfloat16,
)
model = AutoModelForCausalLM.from_pretrained(
    "mistralai/Mistral-7B-v0.1", quantization_config=bnb_config
)
model = prepare_model_for_kbit_training(model)

lora_config = LoraConfig(
    r=16,
    lora_alpha=32,                # alpha = 2 x rank
    target_modules="all-linear",  # all linear layers, QLoRA-style
    lora_dropout=0.05,
    task_type="CAUSAL_LM",
)
model = get_peft_model(model, lora_config)
model.print_trainable_parameters()
RLHF: reward model + PPO

SFT on human demonstrations, then a reward model trained on human rankings, then PPO against that reward (Ouyang et al., 2022). It needs paid labelers and runs four models (policy, reference, reward, value). It suits broad alignment: a 1.3B InstructGPT model was preferred over the 175B GPT-3. The risks are instability and reward over-optimization (Gao et al., 2022).

DPO

No reward model, no RL loop: DPO learns from pairs of preferred and rejected answers with a simple classification-style loss, at close to SFT cost. Use it for tone, style, or what a summary should focus on. Run it on your SFT model, and watch logps/chosen: DPO can also lower the chosen answers' probability (Pal et al., 2024).

GRPO

Reinforcement learning without a critic: the model samples a group of answers per prompt, a reward function scores them, and answers above the group average get reinforced (Shao et al., 2024). Use it when a program can check correctness: math, code with tests, extraction into a fixed schema. The main risk is reward hacking, which is why DeepSeek-R1 avoided neural reward models for reasoning.

Distillation

A large teacher trains a smaller student, most simply through SFT on the teacher's answers: DeepSeek's R1-Distill models used about 800k DeepSeek-R1 samples. Use it when a large model works but is too slow or costly. A student trained on fixed outputs never practices on its own mistakes; check the teacher's license, too.

Model merging

Combine the weights of several fine-tunes of one base model, such as a task fine-tune and a style fine-tune, without training (task arithmetic, TIES-Merging, DARE). You only need an eval set, and mergekit runs on a CPU. The risk is interference, so evaluate every task you care about.
