Why AI document search gets tables wrong, and how to fix it

Many companies now have an AI assistant that answers questions from their documents. "How many API calls does the Business plan include?" The assistant finds the right passage in a PDF, then writes an answer from it.

This works well for normal text. It often fails on tables, and tables are where many answers live: a limit, a price, a dose, a date.

I ran into this while building a question-answering system for long PDFs at a clinical-trial software company. Our pipeline used Docling to keep complex tables intact, retrieve single rows linked to their parent table, and cite the pages and sections behind each answer. This post explains the general technique, with public docs and a made-up table.

The weak point is the first arrow: where you cut. Most tutorials treat a PDF as one long string and cut it every N characters. That is fine for prose. It breaks tables.

Why cutting breaks tables

Take this small table from page 12 of an imaginary product handbook, in section "4.1 Usage limits":

Plan Storage API calls / month Support
Free 5 GB 1,000 Community
Team 100 GB 50,000 Email
Business 1 TB 500,000 Priority

A basic pipeline turns the grid into a stream of words and cuts it every N characters. The title and headers can land in one chunk, and the Business row in the next, mixed with the following section.

Now ask: "How many API calls per month does the Business plan include?" The chunk with "500,000" has no title and no column headers. The Team row's "50,000" sits right before "Business". The AI has to guess which number belongs to which column.

Anthropic describes the same problem for contextual retrieval: "revenue grew by 3%" is useless once the chunk no longer says which company or period. In a table, every cell depends on its row and column headers, so the damage is worse.

The fix: a piece that answers by itself

Store each row with everything it needs to make sense:

A bare row

Business  1 TB  500,000  Priority

Which number is the API limit? The AI must guess.

A row chunk

Table 2: Plan limits
Section 4.1, page 12
Plan: Business
Storage: 1 TB
API calls / month: 500,000
Support: Priority

Every number has its header, and the chunk says where it came from.

Here is the full pipeline. Each step is explained in plain words below it:

  1. Read the layout. Docling sees which parts of the page are text, headings and tables, so a table stays a table.
  2. Cut tables smartly. A small table becomes one chunk. A large table becomes one chunk per row, each with the title and headers. Every row also keeps a link to its full table.
  3. Store everything in one place: a PostgreSQL table, with pgvector for search by meaning.
  4. Search two ways and merge (next section).
  5. Cite the page. Each chunk stores its page and section, so citations come from data, not from the AI's text.

Two searches are better than one

Search by meaning (embeddings) finds rows that say the same thing in other words. Search by exact words finds codes, units and IDs that meaning search can miss. Anthropic's post makes the same point: embeddings "can miss crucial exact matches".

So we run both and merge the two ranked lists with a simple formula, Reciprocal Rank Fusion (RRF): each result gets 1 / (60 + its rank) in each list, and the two scores are added. A result that ranks well in both lists wins. The pgvector README suggests exactly this, based on the original RRF paper.

Table-safe RAG checklist

  • Read the PDF with a layout-aware tool. Never separate a header from its rows.
  • Small tables: one chunk with the title. Large tables: one chunk per row, repeating title, section, page and headers.
  • Link each row to its full table.
  • Combine meaning search and exact-word search.
  • Build citations from stored data, never from the AI's text.
  • Test with real questions about numbers inside tables.

Step 1: parsing tables with Docling (code)

Docling is an open-source (MIT) document converter. Its technical report describes a layout analysis model and TableFormer, a model that recovers table structure. The output keeps tables, reading order and section hierarchy.

Simplified example, based on the Docling docs:

from docling.datamodel.base_models import InputFormat
from docling.datamodel.pipeline_options import PdfPipelineOptions, TableFormerMode
from docling.document_converter import DocumentConverter, PdfFormatOption

opts = PdfPipelineOptions(do_table_structure=True)
opts.table_structure_options.mode = TableFormerMode.ACCURATE  # already the default

converter = DocumentConverter(
    format_options={InputFormat.PDF: PdfFormatOption(pipeline_options=opts)}
)
doc = converter.convert("handbook.pdf").document

for table in doc.tables:
    df = table.export_to_dataframe(doc=doc)  # pandas DataFrame, headers become columns
    print(table.self_ref, table.caption_text(doc), [p.page_no for p in table.prov])

Each table gives you a DataFrame, a caption, and provenance (prov) with the page number and bounding box. If columns come out merged, the docs suggest do_cell_matching = False.

Step 2: chunk sizes, parent links and Docling's HybridChunker

Small tables: one chunk. Keep the table as Markdown with its caption. This suits questions like "compare all plans". The limit is the embedding model: all-MiniLM-L6-v2, for example, truncates input longer than 256 word pieces, so the later rows of a large table never reach the vector.

Large tables: one chunk per row, repeating the table title, the section and page, and the column header next to every value.

Link rows to the parent table. Every row stores a parent_id, so when a row matches, the model can also get the full table with its neighbouring rows and footnotes. This is the "small chunks for search, larger parent for context" idea behind LangChain's ParentDocumentRetriever.

For prose, Docling's HybridChunker splits by structure, then by token count, and contextualize() adds the headings to the text you embed. It also chunks tables, writing cells as "row, column = value" and repeating the header across chunks; chunk.meta.doc_items lets you spot those chunks and decide whether to keep them next to your row chunks.

Step 3: the chunks table in PostgreSQL

One chunks table holds prose, whole tables, and rows. Each record has an id, a kind (text, table or table_row), a parent_id from a row to its table, the section and pages, the content the model reads, a pgvector embedding with an HNSW index, and a generated tsvector column with a GIN index for full-text search.

Step 4: hybrid search with RRF in one SQL query

PostgreSQL's ts_rank_cd is not BM25 (the docs say its ranking functions do not use any global information), but it fills the same keyword role. The query below adapts the pgvector-python RRF example; the paper used k = 60.

Simplified example (psycopg named parameters, with pgvector-python's register_vector):

Show code sql · 30 lines
WITH query AS (
    -- plainto_tsquery ANDs every word; OR them so a full question can still match
    SELECT replace(plainto_tsquery('english', %(question)s)::text, ' & ', ' | ')::tsquery AS q
),
semantic AS (
    SELECT id, RANK() OVER (ORDER BY embedding <=> %(qvec)s) AS rnk
    FROM chunks
    ORDER BY embedding <=> %(qvec)s
    LIMIT 40
),
keyword AS (
    SELECT id, RANK() OVER (ORDER BY ts_rank_cd(tsv, q) DESC) AS rnk
    FROM chunks, query
    WHERE tsv @@ q
    ORDER BY ts_rank_cd(tsv, q) DESC
    LIMIT 40
),
fused AS (
    SELECT COALESCE(s.id, k.id) AS id,
           COALESCE(1.0 / (60 + s.rnk), 0.0) + COALESCE(1.0 / (60 + k.rnk), 0.0) AS score
    FROM semantic s
    FULL OUTER JOIN keyword k ON s.id = k.id
)
SELECT c.id, c.kind, c.content, c.section, c.pages, f.score,
       p.content AS parent_table               -- NULL unless the hit is a row
FROM fused f
JOIN chunks c ON c.id = f.id
LEFT JOIN chunks p ON p.id = c.parent_id
ORDER BY f.score DESC
LIMIT 8;

Two details matter here:

  • AND vs OR. plainto_tsquery and websearch_to_tsquery put an AND between words, so a full question often matches no chunk and your hybrid search quietly becomes vector-only. The replace(... ' & ', ' | ') line turns it into an OR query, and ts_rank_cd still ranks chunks with more matching words higher.
  • Duplicates. A row and its parent table can both match. Group results by COALESCE(parent_id, id) so the same table is not sent to the model twice.
Step 5: citations and bounding boxes

Ask the model to reference chunk IDs, then turn those IDs into "Section 4.1, page 12" in your code.

For visual citations, Docling's provenance also holds a bounding box, and table cells can have their own. Check bbox.coord_origin first: boxes can use a top-left or bottom-left origin, and to_top_left_origin(page_height) converts them for an image overlay.
